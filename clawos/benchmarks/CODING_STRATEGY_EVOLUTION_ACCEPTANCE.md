# 编码协作收益与失败候选验收

## P2 单代理优先

`POST /api/workspace/coding/strategy` 的 `preview` 和 `run` 支持 `auto_route: true`。命令行对应 `--auto-route`。匹配任务的已发布路由优先，固定单代理、固定多代理和配对比较继续可用。

开启后，单代理先提交一轮补丁。只有原公开命令实际执行、行为断言失败、变更成功回滚、模型完整返回且用量已核对时，才有资格启动一次多代理协作。多代理从同一冻结 Git 快照开始，调用、计费 token 和执行时间上限均扣除单代理已用额度。公开和后置测试共同决定交付结果，后置测试不进入升级条件。路由报告可复核阶段顺序、触发条件和剩余预算，保留已执行的两端回执。

把触发条件应用到 P0 的八条已保存单代理记录，五条已验收、一道公开测试失败满足升级条件、一条未进入公开测试阶段、一条回复截断。唯一满足升级条件的题在当时的多代理运行中也失败。该回放用于核对触发行为，历史执行的预算及实现与 P2 有差异。

```powershell
.\clawos\.venv\Scripts\python.exe clawos/scripts/coding_strategy.py preview --auto-route --workspace clawos/output/coding-state --case <frozen-case.json> --url http://127.0.0.1:18932/v1 --model <local-model>
```

执行使用 `run --auto-route --execute`。配对样本与策略发布仍沿用独立冻结任务和原有门槛。

## 评审反例修复与公开题验收

协作评审可以为冻结的调用方需求返回一个可执行反例。当前支持在发生修改的授权 Python 文件中调用公开同步顶层函数，输入和预期输出使用有界 JSON。执行器生成固定命令，在严格 AppContainer 内验证反例。若实际值已经符合预期，评审最多重新定位一次。发现不匹配后，单独的模型调用只看原契约和输入，独立推导预期值。两次推导一致才允许修复，修改范围限定到反例文件。补丁通过同一反例、调用方原命令和契约复验后，复审会看到沙箱实测的修复前后结果。格式截断、无效锚点、重复反例、错误预期或再次评审拒绝均保留证据，交付仍受门禁约束。

### 修复基线配对实验

Aider 原题评分保存多行断言的首个差异和已验证通过用例的标识。完整执行同一套测试后，报告会标出补丁使哪些旧通过用例退化。跳过和预期失败不计为已验证通过。`--repair-baseline candidate` 允许第二轮在隔离工作树中重放已评分的候选补丁，并使用该候选的精确编辑锚点。补丁仍相对于冻结的原题起始代码导出，测试文件独立保存。CLI 默认采用 `starter`，正常单代理回滚路径仍用起始源码。

### 真实仓库缺陷主入口比较

`POST /api/workspace/coding/autonomous` 接收可选的 `test_commands`。执行确认后，它为调用方命令创建隔离工作区，先运行严格沙箱基线，再把失败证据送入工具循环。后续每轮都执行同一组命令。未提供 `focus_paths` 时，代理可搜索并读取可访问的仓库文件；初始范围外的合格源码须经实际读取和重新冻结后才能修改。返回的工作区可供审查，原工作树保持完整。

配对任务选自 Boltons 与 Toolz 的十个历史缺陷。每题冻结上游修复提交的完整父版本，重新建立本地 Git 快照。代理收到问题描述、仓库和公开复现命令，未获得目标路径、上游修复补丁或留出测试。原缺陷与上游修复都在严格沙箱运行公开和留出对照。首次归档预检发现 Windows 的换行转换导致上游补丁不能原样重放，复验使用关闭转换的 Git 归档。两道旧 `iterutils` 题的上游修复也因导入时读取主机名被拒绝，最终题组用另外两道真实历史缺陷替换，保留前期阻塞回执。

## 实际行为

- `CodingStrategyService` 预览并持久化冻结决策。没有已发布策略时，使用调用方明确选择的 single 或 multi 基线；发布策略由原 `RuntimePolicyController` 解析，保留 shadow/canary 分配。执行中或入库前版本变化会拒收。不会自动应用生成的业务补丁。
- 成对比较沿用相同授权范围、原测试／后置命令、模型配置和预算。收益为 `accepted - .10*token_fraction - .05*wall_fraction - .02*call_fraction`；先按任务簇平均重复运行，再对任务簇等权。1000次确定性 bootstrap，检查两个模式采用单侧97.5%下界。至少30个成对任务簇、下界大于0.02才产生建议；建议仍只是候选，不自动改变运行模式。
- 分桶是事先固定的文件数量、Python／混合语言、需求绑定和命令数量。模型配置、执行器见证、预算及提示策略摘要隔离数据。它不是语义任务难度估计，也不是AST依赖图路由。同样任务换ID／路径不增加样本；改写任务文本可能形成新摘要，实际独立性仍需维护者审核。
- 外部导入报告始终标为 imported，不会变成 native-paired。选中模式的单次运行也不能冒充成对实验。任一端缺少完整回答／已知usage、预算超限或存在基础设施问题时，整对不参与收益估计；失败仍留在原报告和诊断列表。这种删失会限制估计适用范围，应连同排除数量审核。
- `CodingEvidenceService` 有界读取并核验计划／任务／报告摘要、调用预留与回答绑定、usage计费和预算谓词、冻结命令及补丁摘要；多代理同时核验原生检查点、执行上下文与回答绑定。每次提议前重新读取并核验原文件，变动即拒绝；数据库保存规范化诊断和摘要，不复制模型文本到反思卡／候选提示。
- 格式、测试和其他流水线失败可以产生反思卡及静态白名单提示候选；重复失败幂等去重。预算、环境、来源完整性和未知传输不会冒充语义失败。分类基于可观察事件，不能证明具体语义根因。候选不新增运行质量信号，不发布、不修改源代码。
- 现有通用配置探针不能证明编码策略收益。`SelfEvolutionManager` 对 `coding.proposal` 与 `coding.strategy.*` 增加 `coding_execution` 缺失门禁，通用回归即使通过仍不能进入 shadow。目前专门的真实基线／候选编码 rollout 评估器尚未实现，编码候选保持未发布；需要后续完成该评估器，再沿用真实新样本、shadow/canary及回滚门禁。
